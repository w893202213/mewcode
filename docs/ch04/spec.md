# 工具系统 Spec

## 背景

MewCode 目前是纯聊天助手：模型只能输出文本，接触不到用户的代码仓库。
用户提出代码问题后，模型只能凭训练记忆猜测文件内容，无法实际读文件、改文件或执行命令验证。
这一步给 MewCode 装上工具系统：模型按需发起工具调用，MewCode 负责执行并把结果回灌进对话历史，
助手从「只能动嘴」变成「能干一件事」（每轮最多执行一个工具，自动循环留待下一章）。

## 目标

- 建立统一工具接口与注册中心，工具元信息可转换为两家 LLM API 认可的工具列表格式
- 六个核心工具：读文件、写文件、改文件、执行命令、按模式找文件、搜代码内容
- 两家协议（Anthropic / OpenAI）都支持流式工具调用的参数碎片拼接与结果回灌
- 工具执行带超时与错误处理，失败信息作为结构化结果回给模型，让它调整而不是崩掉
- 每轮对话最多执行一个工具；执行命令前必须经用户确认

## 功能需求

- F1: 提供统一工具接口：每个工具带有名称、描述、参数 Schema 和执行方法；六个核心工具（读文件、写文件、改文件、执行命令、按模式找文件、搜代码内容）全部实现该接口。
- F2: 提供注册中心：集中登记全部工具，支持按名查找，能把登记的工具转换成 Anthropic 与 OpenAI 两套 API 认可的工具列表格式。
- F3: 发起对话请求时自动携带工具列表；模型发起工具调用时，流式增量被逐片拼接成完整参数 JSON——Anthropic 的 input_json_delta 碎片、OpenAI 的带索引 JSON 参数碎片，两条链路都能正确拼出完整工具名与参数。
- F4: 参数拼接完整后立即执行工具：文件类工具直接执行；执行命令工具必须先经用户确认（y 执行 / n 拒绝），拒绝信息作为工具结果回灌给模型。
- F5: 工具执行结果（成功内容或失败错误信息）结构化回灌进会话历史，下一轮请求中模型能看到本轮的完整工具调用与结果。
- F6: 改文件工具基于原文唯一匹配替换：原文找不到时返回明确错误（提示原文不存在）；匹配到多处时返回明确错误（提示匹配次数与位置）；只有唯一匹配才执行替换。
- F7: 工具执行失败（超时、参数不合法、IO 错误、命令退出码非零等）不导致程序崩溃，失败信息作为结构化错误结果返回给模型。
- F8: 每轮对话最多执行一个工具：模型单次响应含多个工具调用时，只执行第一个，并以明确提示告知其余被忽略（本步边界，下一章 Agent Loop 支持连环调用）。
- F9: TUI 展示工具调用（工具名 + 参数）与执行结果（成功内容摘要或失败信息），用户能看到 Agent 正在干什么。

## 非功能需求

- N1: 每个工具都有执行超时上限（30 秒），超时作为错误结果返回，不悬挂。
- N2: 回灌给模型与展示在 TUI 的工具结果有长度上限（30000 字符），超长截断并附加「已截断」说明，防止上下文与终端被刷爆。
- N3: 文件类工具的相对路径以进程启动时的工作目录为基准解析；模型给出的绝对路径原样使用。
- N4: 工具错误信息一律中文、可读、可操作——包含让模型能自我修正的上下文（如改文件冲突时报匹配次数，读文件报具体路径与原因）。
- N5: 不新增第三方依赖：文件操作用标准库 pathlib，进程执行用 subprocess，内容搜索用 re，按模式找文件用 fnmatch/glob。
- N6: 工具执行失败时，TUI 正常显示错误结果并回到输入行，既有交互（Ctrl+C 中断、双击退出、ProviderError 面板）不受影响。
- N7: 两家协议对工具调用的解析逻辑可脱离网络单独测试（纯逻辑解析，与现有 provider 事件分派测试模式一致）。

## 不做的事

- 不做多工具连环调用 / Agent Loop：模型执行完一个工具后，不会自动继续推理再调下一个工具；执行完本轮即结束，下一章再实现自动循环。
- 不做工具调用前的参数确认：只有「执行命令」有人工确认（每轮最多一次），其余五个工具参数直接执行。
- 不做命令白名单 / 危险命令检测 / 沙箱隔离：确认即执行，安全加固留给后续章节。
- 不做工具列表配置化：六个工具固定注册，不做 YAML 开关或按需增删。
- 不做文件路径越界防护：不拦截超出工作目录的路径读写。
- 不做 MCP（Model Context Protocol）集成与外部工具协议。
- 不做工具执行日志落盘（执行历史仅存于会话内存，进程退出即丢弃，与现有会话行为一致）。

## 验收标准

- AC1（F1）: 六个工具均通过统一接口注册并可执行；直接调用每个工具都能得到结构化结果（内容或错误）。
- AC2（F2）: 注册中心按名能找到全部六个工具；生成的工具列表能被两家 API 认可——mock 服务收到的请求体中 tools 字段包含六个工具的名称、描述与参数 Schema。
- AC3（F3）: mock 服务以分片形式流式返回工具调用（Anthropic 的 input_json_delta 碎片、OpenAI 的带索引 JSON 碎片），两条链路都能拼接出完整工具名与参数。
- AC4（F4）: 执行命令工具：用户输入 y 时命令被执行并返回输出；输入 n 时命令不执行，拒绝信息作为工具结果进入会话。
- AC5（F5）: 执行过工具后发起下一轮请求，请求体包含上一轮的工具调用与结果（Anthropic 为 assistant 消息含 tool_use 块 + user 消息含 tool_result 块；OpenAI 为 assistant 消息含 tool_calls + tool 角色消息）。
- AC6（F6）: 改文件：唯一匹配时替换成功、文件内容变化；零匹配时返回「找不到原文」错误；多处匹配时返回「匹配 N 次」错误并给出位置，文件均未被修改。
- AC7（F7）: 工具超时、参数错误、IO 错误、命令非零退出码均不崩溃，错误以结构化结果返回，TUI 正常回到输入行。
- AC8（F8）: 模型单次响应含两个工具调用时，只有第一个被执行，TUI 明确提示其余被忽略。
- AC9（F9）: TUI 中可见工具名、参数与执行结果（成功摘要或失败信息），且与现有流式渲染、Ctrl+C 中断等交互兼容。
