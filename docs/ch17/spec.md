# 记忆渐进式披露（方案 A：召回工具）Spec

## 背景

- 现状（ch11）：每级记忆目录的索引文件每轮注入系统提示，上限 200 行 / 25KB；笔记全文从不进入对话上下文，只供后台去重判定使用。
- 问题：记忆量增长后，每轮为全部摘要付 token，其中大部分与当前对话无关；而真正有用的细节又取不到。
- 已定方向：渐进式披露——摘要层常驻、细节层按需注入。本期实现方案 A：模型主动调用召回工具。
- 已定决策：① 工具内部用 LLM 判相关；② 摘要层温和瘦身（上限 100 行 / 12KB）。

## 目标

- 模型在需要时能主动召回笔记细节（跨 session 经验可发现、可取得），细节不再自动常驻上下文
- 常驻摘要层减半，控制每轮注入成本
- 不引入新依赖（embedding 等），复用现有 LLM 调用模式

## 功能需求

- F1: 召回工具——模型可调用一个检索工具，传入自然语言 query；工具让 LLM 依据 query 与全部笔记的摘要行挑出最相关的笔记（最多 3 条），返回其全文（frontmatter + 正文）作为工具结果。检索范围覆盖用户级与项目级两类记忆；每条返回内容标注来源（级别 + 笔记标识）。
- F2: 判相关的输出协议——判相关 LLM 使用固定系统提示，约束其只输出选中笔记的标识列表；输出无法解析或判定为无相关时，工具返回「没有找到相关记忆」的成功结果（不报错、不中断对话）。
- F3: 摘要层瘦身——索引文件写回上限从 200 行 / 25KB 收紧为 100 行 / 12KB；已有超限索引在下一次写回时按新上限截断。行格式不变（一行一条摘要）。
- F4: 子 Agent 可用——子 Agent 与主 Agent 一样可以调用召回工具，取到的记忆与主对话取到的内容一致。

## 非功能需求

- N1: 召回延迟有界——单次召回（含 LLM 判相关调用）在工具系统的统一超时预算内完成；常态延迟与一次普通 LLM 补全相当。
- N2: 失败降级不阻断——判相关调用失败（网络错误、服务端错误等）时返回带中文说明的错误结果，对话主流程不受影响；记忆文件本身不会被读取操作损坏。
- N3: 结果长度受统一保护——召回返回内容受工具体系现有的结果截断上限约束。
- N4: 无新依赖——不引入 embedding、向量库或任何新第三方库，复用现有 LLM 调用通路。
- N5: 只读——召回工具为只读工具——不修改任何记忆文件，Plan 模式下同样可用。

## 不做的事

- 不做自动检索：每轮按用户输入自动注入相关笔记（C 方案），本期不实现。
- 不做语义向量检索：不引入 embedding 与向量库（B 方案）。
- 不做用户命令：不新增 `/memory` 之类的交互命令。
- 不做多层分层：维持「摘要 → 细节」两级，不设计第三级。
- 判相关不注入对话历史：LLM 判相关只依据 query 与摘要行，不读最近对话。
- 不改笔记格式：笔记文件与 frontmatter 结构、索引行格式均保持不变（瘦身只收紧行数与字节上限）。
- 不做召回缓存：每次调用现算，无状态、无缓存。

## 验收标准

- AC1: 用语义化 query（不出现笔记名原词，如「上次记录的测试状态情况」）调用召回工具，返回包含对应笔记全文的结果，且每条标注来源（级别 + 笔记标识）。
- AC2: 单次召回返回条数不超过 3。
- AC3: query 与所有记忆无关时，返回「没有找到相关记忆」的成功结果，对话不中断。
- AC4: 构造超过 100 行 / 12KB 的索引，触发写回后落盘文件不超新上限。
- AC5: 按旧上限（200 行 / 25KB）生成的历史索引，在下一次写回后被截断到新上限内。
- AC6: 子 Agent 上下文中调用召回工具，能取到与主对话一致的内容。
- AC7: 真实对话中，模型在需要时主动调用召回工具，并基于取回的记忆继续回答（端到端）。
